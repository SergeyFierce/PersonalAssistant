# План: каркас 9/10 по всем критериям

Ниже — что сделать по каждому критерию, чтобы оценка была не ниже 9/10.

---

## 1. Архитектура (сейчас 7/10 → цель 9/10)

**Проблема:** Нет явного domain-слоя, ViewModel напрямую дергает репозиторий, нет use cases.

**Действия:**

- Ввести тонкий слой **domain**: пакет `core.domain` с use cases (классы или интерфейсы), которые инкапсулируют одну операцию и вызывают репозиторий.
  - Примеры: `GetInitialSettingsUseCase`, `SetThemeUseCase`, `CompleteOnboardingUseCase`, `GetHomeServiceIdUseCase`. ViewModel зависит от use cases, а не от `SettingsRepository` напрямую (репозиторий внедряется в use cases).
  - Либо оставить один общий `SettingsUseCase` с методами `getInitialSettings()`, `setTheme()`, … и внедрять его во ViewModel вместо репозитория.
- Сохранить единый источник истины: репозиторий (и при необходимости use case) как единственная точка доступа к настройкам; экраны не обращаются к репозиторию напрямую, только через ViewModel/use cases.
- Не обязательно разносить по модулям: use cases могут жить в `app` в пакете `core.domain`; главное — явное разделение «presentation → domain → data».

**Результат:** Чёткое разделение слоёв, тестируемость (мокать use cases во ViewModel-тестах), архитектура ближе к Clean — стабильно 9/10.

## 2. Качество кода (сейчас 8/10 → цель 9/10)

**Проблемы:** `runBlocking` в `EncryptedSettingsRepository` init; строка `"encrypted_migration_done"` задублирована (в миграции и в `SettingsRepository.kt` — `MIGRATION_DONE_KEY`); возможны точечные улучшения стиля.

**Действия:**

- **Убрать `runBlocking` из init** (см. п. 3): перенести миграцию в асинхронную инициализацию; после этого в init не должно быть блокирующих вызовов.
- Вынести константу миграции в одно место: использовать общую константу для ключа `encrypted_migration_done` (например, internal const в `SettingsRepository.kt` и использовать её в `EncryptedSettingsRepository` при записи после сбоя миграции), чтобы не дублировать строку.
- Проверить исключения из правил Detekt (MagicNumber и т.д.): оставить только обоснованные; убрать лишние или заменить магические числа на именованные константы.
- Добавить краткий KDoc для всех публичных методов интерфейса `SettingsRepository` и для `ScreenParams`, если ещё не везде есть.

**Результат:** Нет блокировки в конструкторе, нет дублирования строк, единообразный стиль и документация — 9/10.

## 3. Производительность (сейчас 7/10 → цель 9/10)

**Проблема:** `runBlocking` в `EncryptedSettingsRepository` при первом запросе репозитория блокирует поток (часто Main) на время миграции.

**Действия:**

- **Сделать миграцию неблокирующей:**
  - Вариант A: репозиторий при первом обращении к любому `Flow` или к `getInitialSettings()` проверяет флаг «миграция выполнена»; если нет — запускает миграцию в `viewModelScope`/`applicationScope` и до завершения миграции эмитит дефолтные значения (или один раз «loading»), затем перечитывает из EncryptedSharedPreferences и обновляет потоки. Конструктор не вызывает `runBlocking`.
  - Вариант B: в `AppModule` при создании репозитория не ждать миграцию в конструкторе; вместо этого предоставить репозиторий сразу, а миграцию запускать в `Application.onCreate()` в корутине (например, после получения репозитория через EntryPoint) и выполнять в `Dispatchers.IO`. Репозиторий до завершения миграции читает из legacy DataStore (или из Encrypted, если миграция уже была), а после — только из Encrypted. Реализация потребует внутри репозитория состояния «миграция в процессе» и переключения источника данных.
  - Предпочтительно Вариант A с «ленивой» миграцией при первом suspend-вызове (`getInitialSettings()` или при первом collect Flow): в этом вызове запускать миграцию на IO, ждать её завершения (suspend), затем читать из Encrypted и заполнять StateFlow. Конструктор только создаёт EncryptedSharedPreferences и подписывается на listener; миграция — в отдельном suspend-методе, вызываемом из Application/ViewModel при старте.
- Убедиться, что при первом показе экрана (bootstrap) не происходит длительных операций на Main: все тяжёлые операции — в IO/courtine.

**Результат:** Нет блокировки Main при старте, миграция в фоне — 9/10 по производительности.

## 4. Безопасность (сейчас 8/10 → цель 9/10)

**Проблемы:** Нет явного Network Security Config; нет формального аудита логов на чувствительные данные.

**Действия:**

- Добавить **Network Security Config**: создать `res/xml/network_security_config.xml` с `base-config` с `cleartextTrafficPermitted="false"` (если приложение не использует HTTP). Сослаться на него в манифесте в `<application android:networkSecurityConfig="@xml/network_security_config">`.
- Провести **аудит логов**: убедиться, что ни в одном `Log.`* не выводятся ключи, токены, пароли или персональные данные; при необходимости заменить на обобщённые сообщения или убрать логи в release (через ProGuard или проверку BuildConfig.DEBUG).
- В **README** добавить короткий подраздел «Безопасность»: шифрование настроек, fallback, отсутствие cleartext (если так), что секреты не хранятся в коде, ссылка на замену `google-services.json`.

**Результат:** Явная сетевая политика, безопасные логи, документированные практики — 9/10.

## 5. Тестирование (сейчас 7/10 → цель 9/10)

**Проблемы:** Нет unit-тестов для EncryptedSettingsRepository; не покрыта часть логики ViewModel (например, `getInitialServiceIdForMainScreen`); можно усилить тесты репозитория.

**Действия:**

- **Unit-тесты для EncryptedSettingsRepository:** использовать in-memory или тестовый EncryptedSharedPreferences (если библиотека позволяет) либо вынести логику чтения/записи в отдельный внутренний класс/функции и тестировать их с обычным SharedPreferences; альтернатива — тестировать только миграцию (функцию `migrateDataStoreToEncryptedIfNeeded`) с mock DataStore и mock SharedPreferences.
- **Расширить AppStateViewModelTest:** добавить тесты для `getInitialServiceIdForMainScreen` (первый показ vs возврат с настроек) и для сценариев с `hasMainScreenBeenShownThisProcess`; проверить, что при ошибке репозитория эмитится нужный messageEvent.
- **Добавить тест миграции:** unit-тест, который проверяет, что после вызова `migrateDataStoreToEncryptedIfNeeded` с заполненным DataStore все ключи корректно попадают в target SharedPreferences и флаг migration_done установлен.
- Опционально: добавить в CI шаг с **instrumented-тестами** (если есть стабильный эмулятор в GitHub Actions), чтобы защитить от регрессий UI; если не добавлять — зафиксировать в README/CI, что instrumented запускаются вручную или локально.

**Результат:** Покрытие репозитория и ключевой логики ViewModel, тест миграции — 9/10.

## 7. Готовность к продакшену (сейчас 8/10 → цель 9/10)

**Проблемы:** Нет явного чек-листа релиза; стратегия версий не зафиксирована; CI не покрывает instrumented (по желанию).

**Действия:**

- В **README** или в `docs/release.md** добавить короткий **Release checklist**: сборка release, прогон unit-тестов, проверка подписи AAB/APK, подмена` google-services.json` для продакшена, проверка версии (versionCode/versionName). Опционально — шаги перед выкладкой в магазин.
- Зафиксировать **стратегию версий**: например, versionCode инкрементируется при каждом релизе, versionName — семантическое версионирование (MAJOR.MINOR.PATCH); указать это в README или в комментарии в `build.gradle.kts`.
- **CI:** оставить как есть (assembleDebug + testDebugUnitTest) или добавить шаг `assembleRelease` и при возможности — instrumented-тесты на эмуляторе; в любом случае описать в README, что именно прогоняется в CI.

**Результат:** Понятно, как готовить и выкладывать релиз; CI и версии прозрачны — 9/10.
