# Архитектурные решения

Краткое описание ключевых решений проекта Personal Assistant: контекст, выбор и последствия.

---

## 1. EncryptedSharedPreferences и fallback на DataStore

**Контекст.** Настройки (включённые сервисы, избранный, тема, онбординг и т.д.) хранятся на устройстве. Обычный DataStore/SharedPreferences не шифрует данные; при компрометации устройства или доступе к файлам настройки читаемы в открытом виде.

**Решение.** В продакшене используется **EncryptedSharedPreferences** (androidx.security:security-crypto): ключ через MasterKeys, данные шифруются при записи. При первом запуске после обновления с версии на обычном DataStore выполняется **однократная миграция** данных в зашифрованное хранилище. Если создание EncryptedSettingsRepository падает (например, на части эмуляторов или при сбое Keystore), **AppModule** подхватывает исключение и предоставляет **DataStoreSettingsRepository** — обычный DataStore без шифрования.

**Последствия.** Настройки защищены на большинстве устройств; приложение не падает при недоступности шифрования, пользователь сохраняет возможность работать с приложением с деградированной защитой хранилища.

---

## 2. EntryPoint для инициализации темы до первого экрана

**Контекст.** Тему (light/dark) нужно один раз инициализировать по системной настройке при первом запуске, до отрисовки первого экрана. К этому моменту Activity ещё не создана, Hilt-граф для Activity недоступен — инжектировать ViewModel или репозиторий в Activity нельзя.

**Решение.** В **PersonalAssistantApp.onCreate()** репозиторий получают через **Hilt EntryPoint** (`SettingsRepositoryEntryPoint`): EntryPoint даёт доступ к отдельным зависимостям из графа без создания Activity. В корутине (ProcessLifecycleOwner.lifecycleScope) вызывают `ensureMigrationDone()` и `ensureThemeInitialized(context)`; инициализация выполняется до появления UI.

**Последствия.** Пользователь не видит «мигания» темы: первый экран сразу отображается в правильной теме. EntryPoint используется только для этой ранней инициализации; остальное приложение по-прежнему получает зависимости через обычный Hilt.

---

## 3. Один общий AppStateViewModel

**Контекст.** Состояние приложения (включённые сервисы, избранный, последний сервис, онбординг, тема, режим каталога, уведомления) нужно на нескольких экранах: Bootstrap, Onboarding, главный экран с доком, управление сервисами, настройки. Требуется единый источник истины и согласованная навигация/обновление UI.

**Решение.** Один **AppStateViewModel**, внедряемый через Hilt и передаваемый экранам (в т.ч. через общие параметры **ScreenParams**). ViewModel держит `uiState` (combine потоков репозитория), тематические flow (theme, catalogViewMode, notifications), методы записи в репозиторий и единый **messageEvent** для показа снэкбаров при ошибках. Логика «какой сервис показать на главном» (избранный → последний → home при первом показе; последний → избранный → home при возврате с настроек) инкапсулирована в **getInitialServiceIdForMainScreen**.

**Последствия.** Нет дублирования состояния между экранами; изменения настроек сразу отражаются во всех подписчиках; добавление нового экрана сводится к использованию того же ViewModel и ScreenParams.

## 4. Добавление нового сервиса

**Контекст.** Приложение строится вокруг набора сервисов (дела, заметки, финансы и т.д.). Порядок и состав сервисов должны задаваться в одном месте, чтобы док, каталог и онбординг оставались согласованными.

**Решение.** Единственный источник истины — **ServiceRegistry** (`core/model/ServiceRegistry.kt`). Порядок отображения задаётся только списком **displayOrder**; док, каталог и онбординг используют **all** и **groupedByCategory**.

**Как добавить новый сервис (кратко):**

1. **ServiceId** — добавить новое значение в enum.
2. **res/values/strings.xml** — добавить строку названия (например, `service_new_service`).
3. **ServiceRegistry.servicesById** — добавить запись `ServiceId.NEW_SERVICE to AppService(...)` (id, titleResId, route, icon, category).
4. **ServiceRegistry.displayOrder** — вставить новый ServiceId в нужную позицию списка (единственное место, где задаётся порядок во всём приложении).

Подробная инструкция с полями AppService и категориями приведена в KDoc класса **ServiceRegistry**.

## 5. Data‑слой и репозитории для будущих доменов

**Контекст.** Сейчас в приложении есть один домен — «настройки» (enabled services, тема, онбординг и т.д.), реализованный через `SettingsRepository` + `SettingsUseCase`. В будущем планируется добавлять новые домены: дела, заметки, финансы, лекарства и т.п. Чтобы архитектура оставалась близкой к Clean и расширялась предсказуемо, нужен тонкий, но явный каркас data‑слоя.

**Решение.**

1. **Пакет `core.data`**  
   Введён пакет `core.data` с базовыми абстракциями:

   - `RepositoryResult<T>` — typealias к `Result<T>`, единый тип результата для операций репозиториев.
   - `LocalDataSource<Key, Entity>` — каркас для локальных источников данных (БД, DataStore, SharedPreferences, файлы) с методами:
     - `getByKey(key): RepositoryResult<Entity?>`
     - `put(key, value): RepositoryResult<Unit>`
     - `remove(key): RepositoryResult<Unit>`
   - `RemoteDataSource<Request, Response>` — каркас для удалённых источников (HTTP API и т.п.) с методом:
     - `execute(request): RepositoryResult<Response>`

   Эти интерфейсы не навязывают строгую реализацию, но задают общий стиль: все операции возвращают `Result`, исключения не выходят наружу, а типы Request/Response и Entity являются явными моделями слоя данных.

2. **Слой настроек как референс‑пример**  
   Текущий слой настроек (`core/datastore/SettingsRepository.kt` + `core/datastore/EncryptedSettingsRepository.kt` + `core/domain/SettingsUseCase*.kt`) служит эталонным примером:

   - интерфейс `SettingsRepository` реализует слой данных (DataStore/EncryptedSharedPreferences);
   - `SettingsUseCase`/`SettingsUseCaseImpl` инкапсулируют доменную логику и возвращают `Result` наружу;
   - ViewModel (`AppStateViewModel`) и `PersonalAssistantApp` зависят только от use case, а не от конкретного репозитория.

   Новые домены (например, дела/заметки/финансы) должны строиться по тому же принципу: **Repository → UseCase → ViewModel → UI**.

3. **Как добавлять репозиторий и use case для нового домена (шаблон)**  
   Для любого нового домена рекомендуется придерживаться следующего шага:

   1. **Модели домена** — добавить типы в `core/model/` (например, `TaskId`, `Task`, `TaskCategory`), аналогично тому, как устроены `ServiceId`/`AppService`.
   2. **Data‑слой** — в `core.data.<domain>` или `core.datastore.<domain>`:
      - определить интерфейс репозитория (например, `TasksRepository`) с методами уровня домена: `getTasks()`, `addTask()`, `updateTask()`, `deleteTask()` и т.д.;
      - при необходимости выделить локальный источник (`TasksLocalDataSource`) и, в будущем, удалённый (`TasksRemoteDataSource`), опираясь на `LocalDataSource`/`RemoteDataSource` как на каркас.
   3. **Domain‑слой (use cases)** — в `core.domain.<domain>`:
      - либо ввести отдельные классы `GetTasksUseCase`, `CreateTaskUseCase` и т.д.;
      - либо добавить методы в общий use case домена (по аналогии с `SettingsUseCase`), если домен небольшой.
   4. **DI (Hilt)** — в `AppModule` или отдельном Domain/Data‑модуле:
      - предоставить реализации репозитория и use case’ов через `@Provides`/`@Binds`;
      - при необходимости использовать квалификаторы (`@Named`/`@Qualifier`) для разных реализаций (например, mock vs prod).
   5. **ViewModel и UI**:
      - ViewModel получает зависимости только от use case’ов (интерфейсов domain‑слоя);
      - UI (экраны Compose) не знает о репозиториях и data‑слое, работает только с состоянием и методами ViewModel.

**Последствия.**  
Появляется явный, но лёгкий каркас data‑слоя, который:

- не усложняет текущую реализацию (слой настроек уже вписывается в схему и служит референсом);
- позволяет добавлять новые домены (дела, заметки, финансы и т.д.) по одному и тому же шаблону;
- сохраняет чистое разделение: UI ↔ ViewModel ↔ UseCase ↔ Repository ↔ DataSource, с предсказуемым использованием `Result` и чёткими моделями данных.

## 6. Адаптация под планшеты и большие экраны

**Контекст.** Приложение ориентировано не только на телефоны, но и на планшеты, складные устройства и десктопные окна. При большой ширине экрана одноколоночные экраны выглядят «растянутыми», пользователю сложнее сканировать контент.

**Решение.**

- В пакете `core.ui` введена утилита `WindowWidthClass`:
  - `Compact` — ширина < 600dp (типичные телефоны в портретной ориентации);
  - `Medium` — 600–839dp (широкие телефоны, часть планшетов/окон);
  - `Expanded` — ≥ 840dp (планшеты, десктопные окна, складные устройства).
- Компонента `rememberWindowWidthClass()` читает `LocalConfiguration.screenWidthDp` и возвращает текущий класс ширины. Экраны используют его для выбора раскладки.
- Главный экран сервисов (`ServicesMainScreen`):
  - `Compact/Medium` — одноколоночный layout (как на телефонах): один текущий сервис по центру, док внизу.
  - `Expanded` — двухколоночный layout: слева список (панель) доступных сервисов, справа — контент выбранного сервиса.
- Экран «Управление сервисами» (`ManageServicesScreen`):
  - Использует `BoxWithConstraints` и динамически подбирает число колонок в GRID‑режиме на основе ширины (минимальная ширина карточки, верхняя/нижняя границы количества колонок).
- Экран настроек (`SettingsScreen`):
  - Для `Compact/Medium` — как и раньше, вертикальный список в одной колонке.
  - Для `Expanded` — содержимое ограничено по ширине (дополнительные горизонтальные отступы), чтобы на планшете настройки не занимали всю ширину и оставались удобными для чтения.

**Рекомендации для новых экранов.**

- Для экранов, которые должны хорошо выглядеть на планшетах/складных устройствах:
  - внутри композиции вызывайте `val widthClass = rememberWindowWidthClass()`;
  - для `Compact/Medium` делайте одноколоночную раскладку с вертикальным скроллом;
  - для `Expanded` переходите на двух‑ и более‑колоночные раскладки, сайд‑панели, мастер‑детейл и т.п.;
  - не создавайте отдельные "tablet‑версии" экранов — предпочтителен единый composable с адаптивной раскладкой.

## 7. План сетевого слоя и безопасность HTTP

**Контекст.** На текущем этапе приложение не выполняет сетевых запросов, но в будущем планируется интеграция внешних сервисов (синхронизация дел, заметок, финансовых операций и т.д.). Чтобы избежать хаотичного роста сетевого кода, важно заранее определить место для HTTP‑клиента, репозиториев и политики безопасности.

**План интеграции HTTP‑клиента.**

- **Выбор библиотеки.**
  - Базовый вариант — **Retrofit + OkHttp**:
    - Retrofit для декларативных интерфейсов API и автоматической десериализации.
    - OkHttp как низкоуровневый HTTP‑клиент с поддержкой TLS, интерцепторов и SSL pinning.
  - Альтернативный вариант — **Ktor client**, если понадобится мультиплатформенность или единый стек с backend’ом.

- **Где живут интерфейсы API и модели.**
  - Пакет `core.data.remote`:
    - `NetworkClient` и базовые модели/ошибки HTTP (например, `NetworkError`) — общий каркас.
    - Подпакеты для доменов, например:
      - `core.data.remote.tasks.TasksApi`
      - `core.data.remote.notes.NotesApi`
      - `core.data.remote.finance.FinanceApi`
  - DTO‑модели:
    - для стабильных доменов — отдельные пакеты `core.data.remote.<domain>.model` (например, `TasksDto`);
    - преобразование DTO → доменные модели (`Task`, `Note` и т.п.) выполняется в репозиториях домена.

- **Связка с репозиториями и use case.**
  - Для каждого домена с сетью:
    - Репозиторий в `core.data.<domain>` (например, `TasksRepositoryImpl`) зависит от:
      - локальных источников (`LocalDataSource`, БД/DataStore);
      - удалённого API (`TasksApi`, инкапсулирующего Retrofit/Ktor).
    - Репозиторий реализует интерфейс `TasksRepository` и отдаёт `RepositoryResult<DomainModel>`.
    - Use case в `core.domain.<domain>` оперируют только доменными моделями и `RepositoryResult`:
      - содержат бизнес‑правила слияния локальных/удалённых данных;
      - маппят ошибки в понятные UI‑состояния.
  - ViewModel’и (`TasksViewModel` и т.п.) зависят только от use case, а не от Retrofit/OkHttp.

- **Централизованная обработка ошибок.**
  - В `core.data.remote` вводится общее представление сетевых ошибок (`NetworkError`), которое:
    - маппит HTTP‑коды (4xx/5xx), таймауты, отсутствие сети, ошибки десериализации;
    - логируется и, при необходимости, превращается в пользовательские сообщения на уровне use case.
  - `RepositoryResult` на текущем этапе — это typealias к `Result<T>`. При появлении реальных сетевых операций:
    - возможно, будет заменён на собственный sealed‑класс (например, `RepositoryResult.Success/Failure(NetworkError)`), без изменения публичных сигнатур.

**Меры безопасности при работе с сетью.**

- **TLS и запрет cleartext.**
  - Уже используется Network Security Config с `cleartextTrafficPermitted="false"` — только HTTPS.
  - Все базовые URL должны быть HTTPS и контролироваться через конфигурацию (BuildConfig, remote config и т.п.).

- **SSL pinning.**
  - Для критичных запросов (финансы, чувствительные данные) OkHttp будет настроен с `CertificatePinner`, чтобы:
    - пиннить сертификаты/публичные ключи доверенных backend‑серверов;
    - отклонять соединения при несоответствии пинов.
  - Пины и домены хранятся в конфиге, без захардкоженных «секретов», с возможностью обновления при ротации сертификатов.

- **Интерцепторы OkHttp.**
  - **Security‑интерцептор**:
    - добавляет обязательные заголовки (версия приложения, platform, возможно токен аутентификации);
    - централизованно обрабатывает коды 401/403 (например, инициирует logout/refresh‑токена через отдельный use case).
  - **Logging‑интерцептор**:
    - включён только в debug/стейджинг‑сборках;
    - логирует URL, код ответа и укороченное тело **без** персональных данных и секретов (фильтрация полей, маскирование токенов).
  - **Timeout/Retry‑политика**:
    - централизованная настройка таймаутов;
    - ограниченные ретраи только для идемпотентных запросов (GET, безопасные POST по договорённости).

- **Хранение и использование токенов.**
  - Токены аутентификации и refresh‑токены не логируются и не захардкожены.
  - Для хранения используются защищённые механизмы (EncrypedSharedPreferences / SafetyNet / Keystore в зависимости от требований).
  - Обновление токена и logout реализованы как отдельные use case’ы, не смешиваются с обычными репозиториями.

**Минимальный каркас кода.**

- В пакете `core.data.remote` добавлен базовый интерфейс `NetworkClient` и модель `NetworkRequest`:
  - `NetworkClient.execute(request: NetworkRequest<T>): RepositoryResult<T>` — абстракция над конкретным HTTP‑клиентом.
  - `NetworkRequest` содержит идентификатор endpoint’а и описание; в реальной реализации будет расширен полями URL, метода, заголовков и тела.
  - `NetworkError` описывает типы сетевых ошибок (HTTP, таймаут, отсутствие сети, десериализация, неизвестная ошибка).
- На данном этапе этот каркас **не используется** ни одним экраном/репозиторием и не меняет поведение приложения, но задаёт направление для будущих интеграций.

## 8. Ограничение роста AppStateViewModel (анти‑god‑object)

**Текущие обязанности AppStateViewModel.**

На текущем этапе `AppStateViewModel` решает строго «корневые» задачи:

- агрегирует потоки настроек из `SettingsUseCase` в единое состояние `AppStateUiState` (включённые сервисы, избранный, последний, онбординг);
- предоставляет отдельные потоки для темы (`themeFlow`), режима каталога (`servicesCatalogListViewFlow`), уведомлений;
- инкапсулирует выбор стартового сервиса на главном экране (`getInitialServiceIdForMainScreen` + флаг `hasMainScreenBeenShownThisProcess`);
- содержит операции изменения настроек верхнего уровня:
  - включение/отключение сервисов (в т.ч. правило «минимум один сервис»),
  - выбор избранного/последнего сервиса,
  - отметка прохождения онбординга,
  - переключение темы, уведомлений, режима каталога;
- координирует показ одноразовых сообщений об ошибках (`messageEvent`).

То есть ViewModel выступает как единая точка входа к **состоянию настроек и навигации верхнего уровня**, не влезая в детализацию конкретных экранов (доменная логика онбординга вынесена в `SettingsUseCase.completeOnboarding`).

**Когда логика должна выноситься из AppStateViewModel.**

Чтобы `AppStateViewModel` не превратился в god‑object по мере роста проекта, придерживаемся следующих правил:

1. **Новые домены → отдельные ViewModel’ы.**
   - Если новый функциональный блок (дела, заметки, финансы и т.п.) имеет собственное состояние и операции, он **не** добавляется в `AppStateViewModel`.
   - Для каждого значимого домена создаётся свой ViewModel (например, `TasksViewModel`), который:
     - зависит от соответствующих use case’ов (`TasksUseCase`, `FinanceUseCase` и т.п.);
     - живёт в пакете `core.ui` рядом с экраном(ами) этого домена.
   - `AppStateViewModel` при этом может знать только о «флагах верхнего уровня», влияющих на навигацию (например, что пользователь включил/выключил весь домен).

2. **Рост обязанностей внутри настроек.**
   - Если в `AppStateViewModel` появляются методы, явно привязанные к отдельным экранам настроек (например, сложная логика только для "Уведомлений" или "Приватности"), и:
     - файл ViewModel переваливает за **300–400 строк**;
     - или в KDoc/описании обязанностей можно насчитать **больше 3–4 независимых областей ответственности** (Bootstrap/Onboarding, Main, ManageServices, Notifications, Privacy, ...),
   - тогда вводим отдельные ViewModel’ы для соответствующих экранов:
     - `OnboardingViewModel` — если онбординг станет сложнее текущего сценария выбора сервисов;
     - `SettingsViewModel`, `ManageServicesViewModel` — если логика настроек/каталога перестанет быть простыми делегатами к use case.
   - `AppStateViewModel` в этом случае остаётся тонким фасадом над глобальным состоянием ( enabled‑сервисы, тема, онбординг), а «тяжёлые» сценарии живут в специализированных ViewModel’ах.

3. **Сложные бизнес‑правила → в use case/домен.**
   - Как только в `AppStateViewModel` появляется бизнес‑логика, которая:
     - использует больше 2–3 полей состояния одновременно;
     - содержит нетривиальные ветвления/циклы;
   - такую логику выносим в domain‑слой (`core.domain`) как use case или вспомогательный класс, а ViewModel только:
     - собирает входные данные;
     - вызывает use case;
     - публикует результат в UI‑состояние и/или `messageEvent`.
   - Пример уже реализован: онбординг‑логика (`completeOnboarding`) инкапсулирована в `SettingsUseCaseImpl`, а ViewModel лишь делегирует вызов и обрабатывает ошибки.

4. **Технические сигналы к рефакторингу.**
   - В `AppStateViewModel` не добавляем:
     - прямой доступ к нескольким независимым репозиториям (только к одному `SettingsUseCase`, максимум к 1–2 use case’ам настроек);
     - код, напрямую управляющий UI‑анимациями или состоянием конкретных composable (это ответственность экранов/компонентов).
   - Признаки, что пора разбивать:
     - файл `AppStateViewModel.kt` стал трудночитаемым (прокрутка «листает» несколько экранов в IDE);
     - методы логически группируются по отдельным фичам, которые можно вынести в свои классы без круговых зависимостей;
     - тесты для ViewModel начинают покрывать слишком разнородные сценарии (onboarding + main + уведомления + сложная логика ещё одного домена).

**Практический подход при добавлении новой логики.**

- Сначала спрашиваем: «Это **глобальное состояние/настройки**, или состояние конкретного экрана/домена?»
  - **Глобальное** (влияет на несколько экранов, хранится в `SettingsRepository`) → можно добавить в `AppStateViewModel`, но:
    - бизнес‑правила выносить в use case;
    - не смешивать с логикой доменов.
  - **Экран/домен‑специфичное** → отдельный ViewModel или вспомогательный класс/domain use case.
- При росте сложности отдельных сценариев:
- сначала выносим бизнес‑логику в use case;
- затем, при необходимости, вводим специализированный ViewModel для экрана, а `AppStateViewModel` оставляем только для высокоуровневых настроек и навигации.

## 9. Домен «Заметки»

**Контекст.** Домен «Заметки» реализован как самостоятельный вертикальный срез: Room‑таблица, репозиторий, use case, ViewModel и два экрана (список и полноэкранный редактор) в стиле списка/диалога Telegram. Этот домен служит референсом для будущих сервисов (дела, финансы и т.п.).

### 9.1. Доменная модель

Файлы: `core/model/Note.kt`.

- `@JvmInline value class NoteId(val value: Long)` — обёртка над `Long`, чтобы не путать идентификаторы заметок с другими ID и упростить возможную миграцию на UUID.
- `data class Note(...)`:
  - `id: NoteId` — первичный ключ заметки;
  - `title: String` — заголовок (может быть пустым, тогда в UI показывается как одна пробельная строка, чтобы сохранить высоту ряда);
  - `body: String` — полный текст заметки;
  - `createdAt: Long` — время создания (мс с эпохи);
  - `updatedAt: Long` — время последнего изменения, используется для сортировки;
  - `pinned: Boolean` — признак закрепления (аналог pinned‑чатов в Telegram);
  - `isDeleted: Boolean` — мягкое удаление (soft delete): заметка скрывается из списка, но остаётся в БД для возможной синхронизации/восстановления;
  - `hasLocalChanges: Boolean` и `lastLocalChangeAt: Long` — флаги и метка времени локальных изменений, зарезервированы под будущую оффлайн‑синхронизацию.

Таким образом, модель уже учитывает сценарии: закрепление, мягкое удаление, локальные правки и возможные конфликты при синхронизации.

### 9.2. Room‑схема и сортировка

Файлы: `core/data/notes/NoteEntity.kt`, `core/data/notes/NotesDao.kt`.

- Таблица `notes` (`@Entity(tableName = "notes")`) с полями:
  - `id: Long` — `@PrimaryKey(autoGenerate = true)`;
  - `title`, `body`;
  - `createdAt`, `updatedAt`;
  - `pinned: Boolean`;
  - `isDeleted: Boolean` — мягкое удаление;
  - `hasLocalChanges: Boolean`, `lastLocalChangeAt: Long` (`@ColumnInfo(index = true)`) — маркеры локальных изменений.
- DAO `NotesDao`:
  - `observeNotes(): Flow<List<NoteEntity>>` — основной запрос для списка:
    ```sql
    SELECT * FROM notes
    WHERE isDeleted = 0
    ORDER BY pinned DESC, updatedAt DESC
    ```
    Т.е. **закреплённые заметки сверху**, затем остальные по убыванию `updatedAt`, только не удалённые (`isDeleted = 0`).
  - `getNote(id)` — загрузка одной заметки по ID;
  - `upsertNote(entity)` — insert/update с авто‑ID;
  - `markDeleted(id, timestamp)` — мягкое удаление с обновлением временных полей;
  - `togglePinned(id, timestamp)` — переключение `pinned` (только для не удалённых заметок) с обновлением `updatedAt`/`lastLocalChangeAt`.

### 9.3. Репозиторий и use case

Файлы: `core/data/notes/NotesRepository.kt`, `core/domain/notes/NotesUseCase.kt`.

- `NotesRepository`:
  - инкапсулирует `NotesDao` и маппинг `NoteEntity` ↔ `Note`;
  - методы: `observeNotes()`, `getNote(id)`, `createNote(title, body)`, `updateNote(note)`, `togglePinned(id)`, `softDelete(id)`;
  - все операции возвращают `RepositoryResult<T>` (typealias к `Result<T>`), чтобы исключения не выходили наружу.
- `NotesRepositoryImpl`:
  - `observeNotes()` делегирует в `dao.observeNotes()` и маппит сущности в доменные модели;
  - при создании/обновлении/удалении:
    - обновляет `updatedAt`, `hasLocalChanges`, `lastLocalChangeAt` через `timeProvider`;
    - повторно читает запись из DAO, чтобы вернуть актуальное состояние.

- `NotesUseCase`/`NotesUseCaseImpl`:
  - `notesFlow: Flow<List<Note>>` — обёртка над `repository.observeNotes()`; на этом уровне можно будет добавлять дополнительные бизнес‑правила фильтрации;
  - `createNote(title, body)` и `updateNoteContent(id, title, body)`:
    - нормализуют ввод (`trim()` для заголовка и тела);
    - запрещают полностью пустые заметки (оба поля пусты — `Result.failure(IllegalArgumentException)`), чтобы не захламлять список;
    - в update сначала читают существующую заметку, затем создают копию с новым содержимым и делегируют в `repository.updateNote`;
  - `togglePinned(id)` и `deleteNote(id)` (`softDelete`) — тонкие делегаты в репозиторий.

### 9.4. Интеграция с ViewModel и UI

Файлы: `core/ui/NotesViewModel.kt`, `core/ui/NotesScreen.kt`, `core/ui/NoteEditorScreen.kt`, `core/ui/Navigation.kt`, `core/ui/ServicesMainScreen.kt`.

- `NotesViewModel` (`@HiltViewModel`):
  - зависит только от `NotesUseCase`;
  - собирает `notesUseCase.notesFlow` в `StateFlow<NotesUiState>`:
    - маппит `Note` → `NoteListItemUi` (id, `title`, `bodyPreview` с обрезкой до 80 символов, `updatedAtFormatted`, `pinned`);
    - форматирует время как в списке чатов: **сегодня** — `HH:mm`, **вчера** — «Вчера HH:mm», старые даты — `d MMM`;
  - методы:
    - `onCreateNote(title, body)` / `onUpdateNote(id, title, body)` — вызывают use case и при ошибке эмитят `R.string.notes_save_error` в общий `messageEvent`;
    - `onTogglePinned(id)` / `onDeleteNote(id)` — переключают закрепление и мягко удаляют заметку;
    - `getNote(id)` — вспомогательный suspend‑метод для экрана редактора.

- `NotesScreen`:
  - показывает список заметок в стиле списка чатов Telegram:
    - pinned‑заметки сверху, затем тонкий разделитель, затем обычные заметки;
    - строка: заголовок жирным, под ним одна строка превью, справа — форматированное время, слева — индикатор pin (если закреплена);
  - имеет заглушку строки поиска (без фактического поиска на этом этапе);
  - включает FAB «+» в правом нижнем углу, открывающий полноэкранный редактор.

- `NoteEditorScreen`:
  - полноэкранный редактор, похожий на открытый диалог Telegram:
    - AppBar с «Назад» и (для существующей заметки) кнопкой удаления;
    - однострочное поле заголовка и многострочное поле текста с прокруткой;
  - для новых заметок:
    - открывается из FAB (`navigate(NOTE_EDITOR_ROUTE)`), по «Сохранить» вызывает `onCreateNote()` и возвращается на список;
  - для существующих заметок:
    - открывается при клике по строке (`navigate("$NOTE_EDITOR_ROUTE/{id}")`), подгружает данные через `getNote(id)`;
    - по «Сохранить» вызывает `onUpdateNote()`, по кнопке удаления — `onDeleteNote()` с последующим возвратом на список.

- Навигация и главный экран:
  - в `Navigation.kt` зарегистрированы маршруты `NOTE_EDITOR_ROUTE = "notes/editor"` и `"notes/editor/{noteId}"`;
  - `ServicesMainScreen`:
    - для `ServiceId.NOTES` отрисовывает `NotesScreen` c `NotesViewModel`;
    - для остальных сервисов по‑прежнему показывает заглушку «Сервис в разработке» — домен «Заметки» служит **референсом**, а не исключением из архитектуры.
